# 校园后勤与家长会谈接待工作台（浏览器端）

面向校园的**纯浏览器端**工作台，包含两大模块：

1. 教室故障报修、事故封闭、工单维修与课程临时改排；
2. **家长会谈预约与校内接待（feature-5）**：联合/分场预约、口译员与接待室占用、
   门岗访客名册、三状态独立跟踪、共同议题授权、引用/复制两种共享结论结构与逐学生隐私隔离。

技术栈：**React 18 + TypeScript + Vite + IndexedDB + WebWorker + Vitest**，无后端、无外部依赖，
所有数据保存在浏览器本地 IndexedDB，所有状态变更以**只追加事件流**记录，可随时回放。

## 1. 架构与职责

```
src/
├─ types.ts                 领域模型与事件定义（事件溯源；含会谈预约/接待/纪要/支持计划）
├─ db/idb.ts                手写 IndexedDB Promise 封装（events/blobs/drafts/kv）
├─ engine/
│  ├─ reducer.ts            纯函数事件回放：事件流 -> 当前快照
│  ├─ scheduling.ts         排课引擎：候选过滤、方案一/方案二、重叠硬校验
│  ├─ meeting.ts            会谈可行性：联合 vs 分开、窗口/口译/房间/名册校验
│  ├─ access.ts             任教关系可见性：沿引用权限检查、跨学生私有内容拒绝
│  ├─ commands.ts           故障域命令：操作 -> 事件（合并、门控、通知版本、草稿冲突）
│  ├─ meetingCommands.ts    会谈域命令：预约/改期/缺席/签到/结束/纪要/结论/授权拆分
│  ├─ scenario.test.ts      故障业务规则测试（15 个）
│  ├─ meeting.test.ts       会谈业务规则测试（22 个）
│  └─ idb.test.ts           IndexedDB 持久化/回放测试（2 个）
├─ worker/
│  ├─ incident.worker.ts    WebWorker：事件唯一写入口、回放快照、排课/会谈可行性计算
│  └─ client.ts             Worker Promise 客户端
├─ state/store.tsx          React Context：快照、角色、在线开关、模拟时钟、草稿
├─ views/                   故障六工作台 + 接待协调/门岗/口译/教师会谈 四个接待工作台
└─ lib/seed.ts              种子数据：教室课程、王姓家庭两子女、任教关系、接待室、口译员、窗口
```

关键设计：

- **事件溯源 + 可回放**：业务状态（事故、改排、会谈、名册、纪要、支持计划）全部由事件回放得到，
  IndexedDB `events` 表只追加；“事件回放”页提供 seq 滑块，可查看任意历史时刻快照。
- **共同议题与个别记录分别建模**：`SharedConclusion`（不可变、可修订）与 `PrivateEntry`
  （按学生隔离）是两类实体；联合或分场都是家长可选功能，不提供数据模型开关。
- **两种共享结论落地结构都实现为命令路径**：
  - `reference` 引用结构：共同内容只存 **1 份**，两份学生计划各持引用，权限检查沿引用执行；
  - `copy` 复制结构：经批准内容在两份计划中各存 **1 份（共 2 份）**，以 `pairedCopyId`
    建立必须共同核对的副本关系。更正都生成新修订并把两份当前计划置为待核。
- **WebWorker 承担计算与持久化**：回放、换房搜索、候选评估、会谈可行性都在 worker 线程。
- **照片存 IndexedDB Blob**：不上传任何服务器，通过 ObjectURL 预览。

## 2. 本地启动

### 方式 A：Docker Compose（一键启动，推荐）

```bash
docker compose up -d --build
# 打开 http://localhost:8080
docker compose logs -f          # 查看日志
docker compose down             # 停止
```

多阶段构建：Node 22 编译静态资源 → Nginx 1.27 托管（含 SPA 路由回退与静态资源缓存）。

### 方式 B：本地开发（Node 22）

```bash
npm ci                 # 或 npm install
npm run dev            # 开发服务器，默认 http://localhost:5173
npm run build          # 类型检查 + 生产构建到 dist/
npm run preview        # 本地预览生产构建
```

### 测试

```bash
npm test               # vitest run，共 39 个用例（故障 15 + 持久化 2 + 会谈 22）
```

> 本隔离容器内未安装 Docker 守护进程，Dockerfile/compose 已按标准多阶段构建编写，
> 实际镜像构建与容器启动需在装有 Docker 的环境执行；容器内已实际执行的是
> `npm test`、`npm run build` 与 `vite preview` HTTP 冒烟验证（见第 7 节）。

## 5. 本题场景验证步骤（手工操作脚本）

> 任何时候可在“事件回放”页点“重置演示数据”回到初始状态。

### 步骤 1：模拟报修与重复合并

1. 身份切到**林老师**，模拟时钟设 09:40，扫 `B-B201`，选“漏水”，可加照片，提交。
2. 身份切到**周老师**，09:45 扫 `B-B202`，同样选“漏水”，提交。
3. 切到**设施工作台**：两条报修合并为**同一项事故**（第二条标“重复报修·已合并”），
   事故边界自动包含 B201、B202。

### 步骤 2：核准边界、封闭与工单

4. 设施人员把预计修复时间设为 12:00，点“核准边界并封闭房间”——B201/B202
   在 10:00-12:00 封闭（资源页可见红色封闭状态）。
5. 点“生成维修工单”，再切**维修工作台**可见工单；未核准边界时开工单会被拒绝。

### 步骤 3：核对两种改排方案（调度工作台）

候选核查表逐间列出距离、容量、设备、无障碍、安全、全时段空闲与不合格原因
（D301 对 A 班显示“无无障碍通道”，对 B 班显示“课程全时段不空闲”）。

- **方案一（仅移动受影响课程）**：A→C101、B→C102。
  学生分钟 = 24×8 + 18×18 = **516**，通知 2 个班。
- **方案二（弹性换房）**：A→C101、B→D301、S→C102。
  学生分钟 = 24×8 + 18×7 + 12×7 = **402**，比方案一**少 114**，
  但多移动 1 个班、多通知原本未受影响的 S 班。页面同时展示两组数字与通知对象差异。

### 步骤 4：教师确认后才发布

6. 调度员“采用”任一方案 → 方案进入“待教师确认”。
7. 分别切换到方案内每位教师，在教师工作台点“确认改排”；未全部确认时发布按钮禁用并显示进度。
8. 全部确认后调度员发布：每位师生收到**同一版本 v1 通知**（地点、时间一致）；
   课表页显示实际房间，任何同房同时段的重叠移动都会被引擎拒绝（测试覆盖）。

### 步骤 5：复测失败不自动回滚，14:00 复测通过才解封

9. 维修人员标记“已修复”——封闭状态**不变**（必须设施复测）。
10. 时钟设 11:30，设施人员点“复测失败”并记录原因：B201/B202 维持封闭，
    已发布的改排安排**不会按预计修复时间 12:00 自动回滚**（通知与课表均保持）。
11. 时钟设 14:00，点“复测通过并解除封闭”：两间房恢复可用（P 班午后课不受影响），
    但已发布安排仍保留——解封不等于回滚。

### 步骤 6：离线草稿、过期与冲突

12. 顶栏切“离线”：教师仍可查看已下载的带版本通知、保存报修草稿；提交按钮禁用。
13. 草稿 A：时钟拨到课程结束后再联网提交 → 判为**过期**，不能发布。
14. 草稿 B：离线保存草稿后，让该课程被改排发布，再联网提交 → 判为**冲突**，
    旧草稿进入冲突处理，不能覆盖新安排（草稿状态与原因显示在草稿表中）。

### 步骤 7：比较联合与分开的可行性、参会人与通知差别

15. 身份切到**接待协调员**，查看“联合 vs 分开”卡片：
    - 未授权时**联合显示不可行**（原因：缺少家长与两位学生的共享同意）；分开两场始终可行。
    - 联合：1 场、教师确认 2 次、家长通知 1 份、名册 1 批、往返 1；
    - 分开：2 场、教师确认 4 次、家长通知 2 份、名册 2 批、议题切换 2。参会教师去重后同为班主任+数学。

### 步骤 8：授权与预约，资源占用和门岗名册

16. 勾选两位学生同意，点“记录共享同意”；联合转为可行，点“按此方案预约”。
17. 切到**门岗工作台**：有效名册只有**家长与口译员**（教师为校内人员不在访客名册）；
    “今日接待资源”显示接待室与口译员各 1 条占用中。
18. 回协调员对场次“改期”：旧占用变“已释放”、旧名册在门岗页立即消失（事件流仍保留为 void）、
    旧通知标记作废，新占用/名册/通知重建。

### 步骤 9：口译员临时缺席 → 待改期、旧名单失效

19. 重新预约一个**分开**会谈，点“口译缺席”：两场都转**待改期**、口译状态为临时缺席、
    接待室与口译占用全部释放、门岗有效名册清空（旧条目全部 void）。

### 步骤 10：签到/迟到/取消不等于完成，只有主持人能关闭

20. 重新预约，切**门岗**在开场后点“签到（迟到）”：场次仍是“已排期”，不会完成。
21. 切**林老师（班主任）→ 教师·家长会谈**：非主持人看不到开始/结束按钮；
    点“开始会议”，再让家长“离场”（提前离场）——场次保持进行中，**另一场不受影响**。
22. 点“记录结束”才关闭本场；两场都结束后，协调员页该会谈才显示“已完成”。
    取消到访同理：只是回执，预约不会关闭。

### 步骤 11：纪要、引用/复制两种结构与逐学生隐私

23. 结束后在教师页记录纪要：填 80 字共同结论并选**引用**或**复制**结构，
    甲、乙各填 20 字私有补充，提交后定稿。
24. 切到**苏老师**（只教王小明）：支持计划里**没有王小华**；引擎对读取小华私有 20 字的请求直接拒绝
    （自动化用例断言抛“访问被拒”）。同家庭预约不会让兄弟姐妹内容互相可见。
25. 协调员“支持计划治理”可见：引用结构共同内容 **1 份**（两份计划各 1 条引用）；
    复制结构计划内副本 **2 份**且互相配对。对结论做“更正”会生成新修订，**两份当前计划同时置待核**，
    两位教师分别核对后才清除；事件回放滑块可复现更正前只见 rev1 的历史快照。
26. 对某学生点“仅保留自身事项”：其当前计划不再出现该共同结论，但不可变母本、旧纪要与另一方计划保留。

### 步骤 12：撤回共同议题同意 → 立即拆分，旧纪要按原授权保留

27. 协调员点“撤回同意并立即拆分后续会谈”：授权失效、原联合场取消、资源释放、旧名册失效，
    系统自动新建两场 20 分钟个别会谈（新会谈标注“由…拆分”）；此前已定稿的旧纪要与私有补充不删除，
    且不能再凭旧授权记录新的共同结论。

## 7. 数据与隐私

全部数据（事件、草稿、照片、会谈、名册、纪要、支持计划）仅存在当前浏览器的 IndexedDB（库名
`incident-workbench-db`），不发起任何网络请求；清空浏览器站点数据或使用页内
“重置演示数据”即可恢复初始状态。

隐私边界由引擎强制：教师读取在 `engine/access.ts` 按任教关系过滤，共同内容沿引用/副本核对
授权学生范围，私有 `PrivateEntry` 严格按学生隔离；撤销共享或一方收窄范围后，当前计划不再暴露
相应共同内容，但不可变结论与历史纪要始终保留，保证可审计与历史复现。
